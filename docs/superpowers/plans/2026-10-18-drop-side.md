# Drop side (which eye, ear or nostril) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Drops for an eye, ear or nose carry Left / Right / Both per schedule block. The side is required to save, is recorded on every dose, and is shown loudly wherever a dose appears.

**Architecture:** The side types are pure Kotlin in `schedule/`. `Side` is a nullable field on every `ScheduleRule`, so it lives in the schedule JSON and needs no migration. `DropSite` is a new `medications` column. Each dose log records its `DoseSide` (site plus side) in two new `dose_logs` columns, written by every path that creates a log (scan, Today tick, meal dose). History therefore never changes when the medicine is edited later. The UI reads `TodayItem.side` and `DoseLogEntity.doseSide` and never works the side out again.

**Tech Stack:** Kotlin, Jetpack Compose (Material 3), Room 2.6 (KSP, exported schemas), kotlinx.serialization, JUnit4 + Robolectric.

**Spec:** `docs/superpowers/specs/2026-10-18-drop-side-design.md`

## Global Constraints

- The package ID stays `com.medtrack` and the database file stays `medtrack.db`. Existing data must survive: Room DB version 4 → 5, using `MIGRATION_4_5` and a migration test.
- Schedule JSON is read with `ignoreUnknownKeys`. Every new serialized field has a default (`null`), so old JSON still decodes.
- Left and right always mean the **patient's**. The alarm and the editor say "patient's".
- The lock-screen notification (`lockScreenVersion()`) gains nothing. The side appears only in the private notification text.
- Badge colours: `medColors.amber` background with `medColors.onAmber` text. They work in light and dark.
- The badge and the alarm side must have TalkBack text. The alarm text scales with the existing size settings, because it uses `MaterialTheme.typography`.
- Error copy follows the existing step style: a "Dose N: " prefix only when there are several steps.
- Tests run with `JAVA_HOME="/c/Program Files/Android/openjdk/jdk-21.0.8" ./gradlew :app:testDebugUnitTest` (written below as **`gtest`**, with `--tests` filters as given).

## Review Focus

1. **Two blocks at the same minute with different sides.** Dose logs are unique per (medication, dueAt), so one side would silently win. Saving must be refused. *Task 1: `clashingSidesAreRefused`, including Daily against Weekdays and every-N-hours against Daily.*
2. **Switching the block type (Daily → Every N hours) or adding a step.** The chosen side must not vanish. *Task 1: `withKindKeepsSide`, `addedStepCopiesSides`.*
3. **A form change away from Drops while blocks still hold sides.** New doses and the schedule text must show no side, and past logs keep theirs. *Task 2: `sideOfIgnoresSideUnlessSidedDrops`. Task 3: `logKeepsSideAfterMedicineEdited`.*
4. **Ticking an upcoming dose on Today before it rings.** That creates the log through `recordUpcoming`, which must store the side too. *Task 3: `recordUpcomingStoresSide`.*
5. **Meal-triggered drops.** `addMealDose` is a third log-creating path. *Task 3: `mealDoseStoresSide`.*

- Create: `app/src/main/java/com/medtrack/schedule/Sides.kt`

- Test: `app/src/test/java/com/medtrack/schedule/SidesTest.kt`

**Interfaces:**
- Produces:
  - `@Serializable enum class Side { LEFT, RIGHT, BOTH }`
  - `enum class DropSite(val label: String, val sided: Boolean)`, with `EYE("Eye", true)`, `EAR("Ear", true)`, `NOSE("Nose", true)`, `OTHER("Mouth or other", false)`
  - `data class DoseSide(val site: DropSite, val side: Side)`, with:
    - `val label: String`: "Left eye", "Right ear", "Both nostrils", "Both eyes"
    - `val badge: String`: `label.uppercase()`
    - `val patientLabel: String`: "Patient's left eye", or "Both eyes" for BOTH
    - `val short: String`: "Left" / "Right" / "Both"
  - `fun DropSite.question(): String`: "Which eye (patient's)", "Which ear (patient's)", "Which nostril (patient's)"
  - `ScheduleRule.side: Side?`, abstract on the sealed interface. Each data class gets `override val side: Side? = null` as its last constructor parameter.
  - `fun ScheduleRule.withSide(side: Side?): ScheduleRule`
  - `fun ScheduleRule.describe(site: DropSite? = null): String`, `fun Schedule.describe(site: DropSite? = null)`, `fun List<Schedule>.describeSteps(site: DropSite? = null)` and `fun List<Schedule>.describeOn(date: LocalDate, site: DropSite? = null)`. When `site` is non-null and the rule has a side, the rule text ends with `" · " + DoseSide(site, side).label`. All existing texts stay the same when `site` is null.
  - `fun List<Schedule>.sidesValidationError(site: DropSite?): String?`, which returns null when `site` is null or not `sided`.

- [ ] **Step 1: Write the failing tests** in `SidesTest.kt`:
  - `labels`: `DoseSide(EYE, LEFT).label == "Left eye"`, `DoseSide(NOSE, BOTH).label == "Both nostrils"`, `DoseSide(EAR, RIGHT).badge == "RIGHT EAR"`, `DoseSide(EYE, RIGHT).patientLabel == "Patient's right eye"`, `DoseSide(EYE, BOTH).patientLabel == "Both eyes"`.
  - `oldJsonDecodesWithoutSide`: `ScheduleJson.decodeSteps("""[{"rules":[{"type":"daily","times":["08:00"]}],"startDate":"2026-10-18"}]""")[0].rules[0].side == null`. Also, an encode→decode round trip of a `DailyTimes(listOf(8:00), side = Side.LEFT)` keeps `LEFT`.
  - `describeAddsSide`: `Schedule(listOf(DailyTimes([8:00], LEFT), DailyTimes([21:00], RIGHT)), start).describe(DropSite.EYE) == "Daily at 8:00 AM · Left eye; Daily at 9:00 PM · Right eye"`. The same schedule's `.describe()` (no site) is `"Daily at 8:00 AM; Daily at 9:00 PM"`.
  - `withKindKeepsSide`: `DailyTimes([8:00], LEFT).withKind(ScheduleKind.INTERVAL, start).side == LEFT`, and likewise for AFTER_MEAL and WEEKDAYS.
  - `addedStepCopiesSides`: for a one-step list with a LEFT rule, `withAddedStep()[1].rules[0].side == LEFT`.
  - `missingSideIsRefused`:
    - one step, rule side null, `sidesValidationError(EYE) == "Choose which eye"`
    - two steps where step 2 lacks a side → `"Dose 2: choose which eye"`
    - `NOSE` → `"Choose which nostril"`
    - `sidesValidationError(OTHER) == null`, and `sidesValidationError(null) == null`
  - `clashingSidesAreRefused`:
    - `DailyTimes([8:00], LEFT)` + `DailyTimes([8:00], RIGHT)` → `"8:00 AM is set for two sides – choose Both instead"`
    - `DailyTimes([8:00], LEFT)` + `Weekdays({MON}, [8:00], RIGHT)` → the same error
    - `EveryNHours(6, start.atTime(8:00), LEFT)` + `DailyTimes([14:00], RIGHT)` → `"2:00 PM is set for two sides – choose Both instead"`
    - the same time with the same side → null
    - two steps → prefixed `"Dose 2: "`

- [ ] **Step 3: Implement.**
  - `Sides.kt` holds the types and labels above, plus `sidesValidationError`. The missing-side check comes first, then the clash check. The words per site: eye/eyes, ear/ears, nostril/nostrils.
  - **Clash algorithm.** For each step, take every rule with a non-null side and compute `dosesBetween(step, rule, from = step.startDate.atStartOfDay(UTC) - 1 ms, to = from + 7 days, ZoneOffset.UTC)`. Group the instants across rules. The first instant (in time order) that has more than one distinct side gives the error, with the time formatted by `TIME_12`. Seven days covers the weekly pattern, because every-N-hours restarts each day.

  - `withKind` passes `side` into the new rule.
  - Thread `site` through the four describe functions. `RuleBlock`'s header in the editor stays `rule.describe()` for now; Task 4 changes it.
